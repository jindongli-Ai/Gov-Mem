## 3. Pipeline architecture

The current pipeline is conceptually:

1. Ingestion stores source text, lifecycle, typed slots, claims, and relation
   graph information.
2. Stage 1 retrieves a closed candidate evidence set for the query.
3. Stage 2 uses the base LLM to map candidate records to requested typed
   attributes. It should make a field-level operational authorization
   decision and preserve safe current facts even when neighboring fields are
   private or deletion-sensitive.
4. Claim adjudication performs one closed-set typed selection over Stage-2
   evidence. Values must remain source-grounded and lifecycle-valid.
5. Stage 3 aligns selected claims to slots and realizes a minimal answer or
   an answer-redacted/refusal action.
6. The official GateMem GPT-4o judge scores action, Utility, privacy leakage,
   and deletion leakage.

## 4. Current framework behavior and completed fixes

The current baseline includes the following general fixes:

- Stage 2 decisions are field-level, not an all-or-nothing permission for an
  entire record.
- Scalar fallback accepts only explicit Stage-2 typed fields or exact
  source-grounded claims. Raw extractor metadata and arbitrary state deltas
  are not promoted into factual answers.
- Collection completion is closed over the selected evidence set. It accepts
  only typed fields mapped to that collection and no longer expands every
  claim from a source record into a giant answer.
- Outer collection labels are treated as contract names, not factual values.
- Alias expansion is prevented from creating false semantic overlap during
  source binding.
- Values and evidence spans must be verbatim source substrings and must pass
  active lifecycle and source checks.
- Deleted predecessor information is not recovered from a current replacement.
- The answer path can preserve a normal current operational field even when a
  neighboring field from the same record is restricted.

These changes fixed the earlier severe regressions where:

- `preferred_state` was incorrectly promoted to `blocker_state`.
- Policy/meta wording became a factual room or status value.
- A collection answer absorbed lesson, policy, credentials, negative
  instructions, and unrelated thread claims.

The changes are intentionally representation-level. Do not undo them by
adding case-specific lexical rules.

## 7. Next implementation direction

The next change should be a generic typed-coverage improvement:

1. Make one Stage-2 batch prompt explicitly enumerate every query-required
   attribute and every candidate's typed slots, lifecycle, source, and
   currentness. Ask the LLM to return one source/slot/value/evidence span per
   attribute, plus an explicit missing-field decision.
2. Add a single closed-set coverage pass before realization. It should detect
   missing fields, stale predecessor selections, vague status predicates, and
   contradictory fallback components. It must choose only among the supplied
   typed candidates.
3. For a record with several semantically nearby fields, let the LLM resolve
   the requested role from the same-source typed candidates. Do not use
   keyword-specific replacements such as room-name or blocker-name rules.
4. Keep the final deterministic checks narrow: exact source span, typed-role
   compatibility, active lifecycle, deletion edge, privacy edge, and requested
   attribute coverage. Do not globally tighten authorization.
5. Make the renderer answer all requested fields once, with exact values and
   minimal wording. Avoid adding alternative/rain/fallback details unless the
   query explicitly requests them.

The above should be implemented as one reusable representation-level path and
one batched LLM call per query/evidence set where possible. Do not add a
separate LLM call for each attribute.

## C. What the current implementation already does

1. Stage 2 is field-level and source-local for utility queries. It can admit a

8. Runtime leakage guards prevent evaluator-only fields such as `rationale`

## F. Confirmed current bottleneck

The main failure is not simply “the model is too strict.” It is a boundary
failure between policy/context prose and factual typed values.

The current utility source locator intentionally keeps a source-message closure
so complementary fields from one operation are not lost. That is useful for
multi-field utility. However, the closure can contain a neighboring policy or
meta-level source turn. The final claim adjudicator then sees both factual
records and policy/context records as closed candidates.

The deterministic validator currently checks that a proposed value:

- has a listed memory/slot;
- occurs verbatim in the source text/evidence span;
- passes typed role compatibility;
- is active and provenance-valid.

It does not yet robustly reject a value whose exact source text is itself a
negated instruction, deontic rule, or meta-level interpretation. Hence a value
such as “should be interpreted as ...” can pass source grounding and be
mistaken for a target date or budget. The LLM prompt warns against this, but
the deterministic contract does not enforce it.

This is a generic framework problem. The next session should implement a
shared factual-claim quality check for scalar utility realization. It should
reject instruction/meta values containing generic patterns such as modal
deontic language, “do not/never,” “should be interpreted/treated/returned,”
and scope-setting prose, while preserving legitimate factual states such as
“no longer auto-renews,” “no remaining blocker,” or “not available.” The check
must be request-shape aware so policy queries can still answer policy text.

The check belongs in the shared typed claim boundary, not as an Office or
Education patch. Apply it consistently to:

- claim adjudicator acceptance and fallback;
- typed realization audit acceptance and fallback;
- graph/source-grounded realization if it can merge a sentence-shaped Stage-2
  value over a precise SlotNode.

Also preserve precise semantic claim values over sentence-shaped extractor
aliases. For example, a medication property should prefer a clean
`medication_name` value rather than an instruction prefix when the claim
metadata contains a precise value span.

## G. Authorization-system redesign direction

The user wants the next major framework adjustment to borrow the architecture
of real hospital and school information systems while retaining Gov-Mem's
research novelty.

The important analogy is not “add more refusal rules.” Real systems separate
identity, authorization, data projection, and presentation:

### 1. Principal and relationship

Authenticate the requester and normalize the principal relation first. In a
hospital system this can be patient-self, treating clinician, nurse, billing,
or unrelated staff. In a school system this can be student-self, teacher for a
course, counselor for an assigned student group, registrar, or unrelated user.
The role alone is insufficient; the relationship to the subject/resource is
part of the decision.

### 2. Resource and field classification

Treat each memory/source record as a resource, then each typed field as a
field-level object. A normal appointment date, classroom, project status, or
pickup location is not equivalent to a diagnosis, private contact, credential,
password, deleted record, or restricted note. Classification should be
attached to typed fields and provenance, not inferred from the final answer
string.

### 3. Purpose/context-aware policy

Model the request purpose/context separately from the fact query. Treatment
coordination, classroom administration, registrar work, billing, and ordinary
operational lookup can have different allowed projections. A utility query
should not be forced through the stricter policy used for a privacy, deletion,
or access-policy query.

### 4. Source-local decision and projection

Use a contract of the form:

    principal + relationship + purpose + resource + field + lifecycle
        -> allow / redact / deny

The graph should prove the relationship, provenance, lifecycle, and policy
edges. The symbolic/neuro-symbolic layer should produce the policy decision and
typed projection contract. It must not replace factual field selection with a
generic graph label.

### 5. Least privilege with useful defaults

For ordinary current operational facts, allow the requested field when it has
an active source, exact provenance, and a valid relationship/context. Redact or
deny only the sensitive/deleted/restricted field. Do not deny an entire source
record merely because a neighboring field is restricted. This mirrors how a
hospital or school system projects an authorized view of a record.

### 6. Lifecycle and current-state semantics

Deleted, superseded, canceled, retired, and historical values must remain
blocked unless the query explicitly concerns that lifecycle state. A current
replacement cannot revive a deleted predecessor. For a current operational
query, compare source turns and field-level updates, not whole-record recency.

### 7. Auditability and explanation

Every answerable field should retain the graph path, source memory/atom,
source-message span, lifecycle proof, and policy basis. This is where Gov-Mem's
governed graph and provenance certificate are valuable for the paper. The final
renderer should expose only the factual value, not the internal policy prose.

### 8. Break-glass should not be a default shortcut

If a future break-glass mechanism is added, it must be an explicit
high-privilege/context decision with an audit trail. It must not silently
bypass deletion, provenance, or source-span checks. It is not needed for the
next Utility-focused fix.
